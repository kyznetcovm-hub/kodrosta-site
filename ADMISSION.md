# Билеты премии: приглашения и команда входа

## Вход хостес через Telegram (обновление готовится к публикации)

Ссылка сотруднику: https://t.me/KodrostaAssistant_bot?start=hostess

1. Бот показывает «Вход для хостес», без запроса телефона и членства в клубе.
2. При первом открытии сотрудник нажимает «Запросить доступ».
3. Организатор: /menu → «Билеты премии» → «Команда входа» → сверить аккаунт → «Разрешить доступ».
4. Сотрудник нажимает «Проверить доступ». В следующие открытия допуск определяется автоматически.
5. «Отозвать доступ» закрывает новые запросы даже из уже открытого приложения.

Доступ привязан к числовому Telegram ID из проверенной подписи initData, отдельно
на событие. Совпадение @username доступа не даёт. Самостоятельный повтор заявки
не снимает отказ/отзыв. Одобряет только администратор; хостес не получает выпуск
билетов, QR других гостей, управление командой и доступ в «Офис».
Каждый проход записывает `host:<Telegram ID>`. Общий ключ больше не принимается.

На iOS/Android используется встроенный сканер Telegram (`showScanQrPopup`, SDK 6.4+),
в остальных клиентах — камера браузера или поиск по имени. Реальное устройство
нужно проверить после публикации: успешная проверка SDK в тесте не подтверждает
работу камеры конкретного телефона.

`GET/POST /api/admission/access` — собственное состояние/заявка подписанного аккаунта;
`GET/POST /api/admission/staff` — список и одобрение/отзыв только для организатора.
Схема `0017_admission_staff.sql` также создаётся обработчиком при первом обращении.

## Запуск демонстрации

Нужен Node.js 24 (используется встроенный SQLite).

Из папки сайта:

```sh
node scripts/admission-demo-server.mjs
```

Открыть `http://127.0.0.1:8789/admission` на том же компьютере.
Сервер слушает только 127.0.0.1: эта ссылка не предназначена для открытия с другого телефона.
База — `.wrangler/admission-demo.sqlite`, отдельно от реальной D1, исключена из Git.
Без снимка оплат при первом запуске создаются десять вымышленных гостей; при перезапуске входы сохраняются.
Если есть `.wrangler/admission-sheet-snapshot.json`, сервер показывает отдельное
тестовое событие `premiya-2026-sheet-demo` с оплаченными гостями из этого снимка.
Это не живая синхронизация: время снимка явно показано в интерфейсе организатора.
Личные контакты в снимок не включены. Файл исключён из Git, через HTTP не раздаётся.
В демонстрации нет обращений к боевому API, отправки сообщений и чтения реальных участников.

## Что проверить

1. Войти как организатор, открыть билет Анны Смирновой в новой вкладке.
2. Убедиться, что просмотр приглашения не меняет число пришедших.
3. Скопировать ссылку на билет, выйти, войти как хостес.
4. Вставить ссылку в поле ручной проверки: получить зелёный результат и один проход.
5. Повторить проверку: красный результат и время первого прохода.
6. Роман Белов ожидает подтверждения, Дарья Морозова — отменённый билет: оба не проходят.
7. Организатор может добавить и подтвердить нового гостя; хостес видит только проверку и поиск.
8. После перезапуска сервера проход Анны остаётся зарегистрированным.

Камера работает в HTTPS или localhost с разрешения пользователя. Есть встроенный
BarcodeDetector и запасной JS-декодер для браузеров без него. До отдельной проверки
на реальных iPhone и Android совместимость камеры не считается подтверждённой.

## Архитектура

- `admission.html`, `css/admission.css`, `js/admission.js`: организатор, хостес, билет.
- `src/admission.js`: API Worker, выдача, подтверждение, отмена, проверка входа.
- `src/admission-sync.js`: проверка исходных оплат и однократная выдача билета по постоянному ID.
- `migrations/0015_admission.sql`: новая таблица; существующие регистрации не меняются.
- `scripts/admission-demo-server.mjs`: локальный SQLite и две тестовые роли.
- `scripts/test-admission.mjs`: доступ, статусы, отсутствие списания при просмотре,
  изоляция событий, одновременный вход, сохранение истории при отмене/подтверждении.

QR содержит ссылку с 256-битным случайным токеном во фрагменте `#t=`.
Он не попадает в URL HTTP-запросов. Сервер получает его в теле POST.
Регистрация входа — один `UPDATE ... WHERE status='active' AND checked_in_at IS NULL RETURNING *`.
Из двух конкурирующих запросов зелёный результат получает ровно один.
Имя гостя выводится для сверки; передача копии билета другому человеку не исключена.
Повторный вход/выход и сброс прохода пока не предусмотрены.

## Перед подключением к премии

### Источник оплат

Создана Google-таблица: https://docs.google.com/spreadsheets/d/1ijK5DZzrNirXqd7W92cMX00obD_AEegX8XmOxiBcq88/edit

Лист `Билеты`, sheetId `1646324108`, заголовки A7:L7, данные A8:L207.
Одна строка — один гость/билет; постоянный ID в A, имя в B, компания в C,
контакт в D, формат в E, стоимость в F, распределённая сумма оплаты в G,
статус оплаты в H, дата оплаты в I, расчётный остаток в J,
готовность к выпуску в K, комментарий в L. Плательщик удалён по запросу пользователя.
Опции H: `Оплачено` (зелёная ячейка), `Не оплачено` (красная),
`Ожидаем оплаты` (жёлтая; заявки). Старое `Подтверждена` перенесено в `Оплачено`.
Тарифы E и автоматический расчёт F: `Гость` = 7000 ₽, `Гость + игра` = 10000 ₽,
`Гость + подкаст` = 12000 ₽, `Гость + игра + подкаст` = 15000 ₽.
Все четыре тарифа и три цвета проверены в Google Sheets, тестовые значения убраны.
Дата I: типизированная дата, формат dd.mm.yyyy, валидация DATE_IS_VALID. Внутри
таблицы колонка I без columnType, чтобы разрешить календарь в пустых ячейках.
Двойной щелчок открывает календарь, затем дата выбирается одним кликом.
В интерфейсе проверен календарь ноября 2026, существующие даты сохранены.
Готовность `К выпуску` требует положительной стоимости, полной полученной суммы,
статуса `Оплачено` и даты. Номер платежа больше не требуется. При общей оплате сумма
распределяется по билетам, а не повторяется целиком в каждой строке.
Проверка этих условий прошла и в самом Google Sheets; временные тестовые данные удалены.
Добавлен администраторский `POST /api/admission/sync` и кнопка обновления из таблицы.
Сервер сверяет исходные поля B:I и тарифы, связывает записи по неизменяемому ID,
не дублирует билеты при повторной загрузке и не сбрасывает зарегистрированный
проход. Новые билеты выпускаются только полностью оплатившим с датой оплаты.
При недоплате или отмене активный билет отзывается после успешной синхронизации.
Билеты, связанные с оплатой, нельзя подтвердить вручную в обход таблицы.
Парсер не доверяет вычисленной колонке «К выпуску». Запросы выполняются транзакцией;
более старый параллельный запрос не перезаписывает более свежую синхронизацию.
Отсутствие строки/сбой чтения сами по себе не должны автоматически удалять билеты.
QR-токены не должны попадать в таблицу учёта оплат.
Изменения статусов применяются при нажатии кнопки; фоновой синхронизации пока нет.
Не считать отмену применённой, пока организатор не получил успешный отчёт обновления.

На снимке первой реальной оплаченной записи проверено: выпуск одного билета,
просмотр без списания, зелёный первый вход, красный повторный, тот же QR и проход
после повторной загрузки. Проверка выполнялась в изолированной памяти, без реального
чекина гостя в боевой базе. Пройдены 40 тестов (в том числе офис и рандомайзер).

Для живого чтения на сервере нужны `ADMISSION_SHEET_ID` (задан в wrangler.jsonc),
существующий секрет `GOOGLE_SERVICE_ACCOUNT_JSON` и доступ этого сервисного аккаунта
**на чтение именно к таблице оплат**. 19 ноября 2026 аккаунту
`kodrosta-sheets-reader@kodrosta-bot.iam.gserviceaccount.com` выдано и проверено
право `reader` на таблицу оплат. Это тот же сервисный аккаунт, который уже читает
таблицу резидентов. 20 ноября Михаил подтвердил живое чтение оплат: в опубликованном
кабинете видны три гостя из таблицы, их тарифы и действующие приглашения.
Доступ всем по ссылке не включался.
Источник оплат не заменяет таблицу резидентов `GOOGLE_SHEET_ID`.
