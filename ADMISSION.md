# Билеты премии — работа команды через Telegram

## Новая схема (подготовлена, публикация ожидает разрешения)

Одна ссылка менеджерам: https://t.me/KodrostaAssistant_bot?start=tickets

1. До авторизации бот показывает только кнопку «Запросить авторизацию».
2. Михаил получает личное сообщение с именем, @username, Telegram ID и кнопками «Да» / «Нет».
3. После подтверждения сотруднику приходит кнопка входа в систему билетов.
4. После отказа можно подать новую заявку. Старые кнопки не влияют на новую заявку.
5. Менеджер добавляет гостя и выбирает пакет (7 000 / 10 000 / 12 000 / 15 000 ₽).
6. Когда менеджер сообщает о полной оплате, Михаил получает карточку гостя, пакет, сумму и комментарий.
7. Только Михаил нажимает «Оплата прошла». До этого ссылка на новый билет менеджеру не выдаётся, вход не разрешён.
8. После подтверждения «Отправить билет» открывает готовый текст и выбор переписки в Telegram; отправляет сам менеджер.
9. Все допущенные менеджеры видят весь список и общую статистику. Автообновление — каждые 5 секунд, есть ручное обновление.
10. Все менеджеры могут сканировать оплаченные билеты; первый проход зелёный, повторный красный.

Получатель и владелец подтверждений: ADMISSION_OWNER_USERNAME=mytolstoy.
Его числовой Telegram ID берётся из уже привязанной записи в residents.
Корпоративный @Kodrosta сохраняет доступ к добавлению/отправке/сканированию,
но не может подтверждать доступ или оплату вместо Михаила.
Новых прав на Google-таблицу никому не выдаётся.

## Проверка менеджерского режима владельцем

У Михаила кнопка «Билеты премии» и ссылка start=tickets открывают два варианта:
«Зайти как организатор» и «Зайти как менеджер». В менеджерском режиме
запросы помечаются x-admission-view=manager; сервер снижает права владельца,
блокируя подтверждение оплат и доступов. Организаторский режим сохраняет права.
Чужой аккаунт не получает права организатора через параметры URL.
Проверка использует общую базу: добавлять гостя «ТЕСТ», а затем отменять его.

## База и прежние гости

Рабочая база билетов — существующая Cloudflare D1. Google-таблица остаётся
историческим реестром; новый рабочий процесс не читает и не обновляет её.
Кнопка «Обновить из таблицы» удалена. Старый POST /api/admission/sync возвращает
410, чтобы загрузка таблицы не могла отменить решение Михаила в боте.
Уже импортированные гости, действующие билеты, QR и история проходов сохраняются.
Тесты старого импорта остаются для проверки совместимости его данных.

## Права и защита решений

- Вход — проверенная подпись Telegram initData и числовой ID, отдельно на событие.
- После отзыва новые запросы открытой сессии перестают проходить.
- Менеджер добавляет гостя в pending; API подтверждения и управления доступом доступны только владельцу.
- Номер заявки — случайные 128 бит, менеджеру он не выдаётся; кнопки решений получает только владелец.
- Callback решения проверяет числовой ID и личный чат владельца, а перед изменением базы
  Telegram должен подтвердить действительность callback_query_id. Сфабрикованный callback ничего не меняет.
- Решение и изменение допуска/билета выполняются одной D1-транзакцией.
  Одновременные «Да» и «Нет» не могут примениться оба; повтор возвращает сохранённый результат.
- Отклонённую оплату можно заявить повторно; прежняя кнопка новую оплату не подтверждает.
- Сбой доставки сохраняет заявку. Повторная отправка использует ту же pending-заявку.
  Владелец также видит ожидающие заявки в кабинете.
- Проверка входа — атомарный UPDATE с условием status=active AND checked_in_at IS NULL.
  ID проверяющего и время первого прохода сохраняются.
- Ссылка на билет выдаётся отдельным POST /share только при status=active.
  Список гостей не раскрывает QR-токены. Просмотр и сохранение приглашения не регистрируют вход.
- Открытая публичная страница webhook существующего бота не меняется этой задачей;
  новые кнопки защищены проверкой Telegram callback и одноразовыми закрытыми ID заявок.

## Приглашение

Страница и сохраняемый PNG содержат пакет «Премия + …», 27 ноября 2026,
начало в 18:30, ЦУМ, ул. Московская, 2, коктейльный дресс-код и @Kodrosta.
QR содержит случайный токен во фрагменте #t= и проверяется только сервером.
Гостю входить в бота не нужно.
На iOS/Android используется встроенный сканер Telegram, остальные клиенты
используют камеру браузера или ручной поиск. Проверка на реальном телефоне
отдельным тестовым билетом нужна после развёртывания новой схемы.

## Исходники

- src/admission.js — API гостей, авторизации, отправки, оплаты и входа.
- src/admission-workflow.js — доставка заявок и решения владельца через Telegram.
- src/engagement.js — ссылка start=tickets и обработка кнопок бота.
- admission.html, js/admission.js, css/admission.css — кабинет команды и приглашение.
- migrations/0018_admission_workflow.sql — метаданные билетов и заявки;
  схема также создаётся при первом обращении. Старые миграции и записи сохраняются.

## Локальная демонстрация

node scripts/admission-demo-server.mjs
http://127.0.0.1:8789/admission

Node 24, SQLite в .wrangler/admission-demo.sqlite, роли «Я организатор» / «Я хостес».
Демо-бот не обращается к Telegram; заявки проверяются через панель владельца в демо.
Если есть приватный .wrangler/admission-sheet-snapshot.json, он загружается при
старте в отдельное demo-событие. Это тестовый снимок, а не рабочая синхронизация.
Файлы .wrangler исключены из Git и не раздаются по HTTP.

## После разрешения на публикацию

1. Проверить корпоративный аккаунт и отдельный аккаунт сотрудника по ссылке start=tickets.
2. Заявку сотрудника подтвердить/отклонить из личного чата Михаила; проверить повтор после отказа.
3. На отдельном тестовом госте проверить запрос оплаты и кнопку владельца.
4. Проверить отправку ссылки, камеру и общий счётчик на двух устройствах.
5. Отменить тестовый билет. Реальных гостей до премии не отмечать пришедшими.
